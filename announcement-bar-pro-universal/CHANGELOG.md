# Changelog (universal package)

## 2.4.1 — 2026-11-07
- **Cloudflare Turnstile (optional anti-bot check of the e-mail sign-up form):** *Settings → E-mail sign-ups* has "Turnstile site key" and "Turnstile secret key" (format-checked: site key `[0-9A-Za-z_-]{10,100}`, secret `[0-9A-Za-z_.-]{10,200}`; Cloudflare's test keys pass). On only when both are set. The secret is **never printed**: the admin shows an empty password field with "saved — leave empty to keep it" and a "Remove the saved secret key" box (an empty site key also switches Turnstile off); saving with an empty field keeps the stored secret; it is not part of the storefront HTML, the JS configuration, the message export / import or the sign-up CSV. On the storefront the sign-up form gets `data-ts` (site key), `data-ts-wait`, `data-err-ts` and a `.abp-ts` box (never in the admin live preview); the shared script loads `challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` only on pages with such a form — with "Wait for cookie consent" only after `window.abpConsent === true` — and renders the widget (`interaction-only`, action `abp-signup`). The sign-up endpoint keeps every earlier check (same origin, session-bound form token, honeypot, per-visitor and per-shop limits, address and consent) and then, right before the sign-up is stored, checks `cf-turnstile-response` with Cloudflare `siteverify` (secret, token, the same client IP as the rate limit — CloudFlare-aware; curl with TLS verification — retried once with the system certificate store when PHP has no CA bundle (curl errors 60 / 77), still verified — else an https stream; 8 s). **Fail closed:** no token → "Please wait a moment until the anti-bot check is done, then send again."; refused token, another action, network error or bad JSON → "The anti-bot check failed. Please reload the page and try again." (nothing stored, the widget is reset). A missing / wrong secret or an unreachable Cloudflare is written to the OpenCart error log (error codes only). The parsing / verification logic lives in the shared `features.php` (`tsVerify()` with an injectable transport, unit-tested with a mocked `siteverify`). New strings in EN / LV / RU (admin + storefront); privacy notes in the README and the admin help: with Turnstile on, Cloudflare processes the visitor's IP address and browser data on pages with a sign-up form.
- **Re-subscribe rule (security / GDPR):** a third party re-submitting an address that had unsubscribed (status 2) went through `saveSubscriber()`, whose `INSERT … ON DUPLICATE KEY UPDATE` overwrote the unsubscribe record (status, token, unsubscribe hash, consent, date added). Now: with double opt-in off nothing changes (as before, same answer); with double opt-in on only the SHA-256 of a new confirmation token is stored in that row (`setResubscribeToken()`, `token` column only) and the confirmation e-mail is sent — status, unsubscribe hash, consent, language, message and dates stay untouched (the 3 mails per address per 24 h limit still applies). Confirmation tokens are now `8 hex digits of the creation time + 56 random hex digits`; only the hash of the whole token is stored and looked up, so the time cannot be changed. The unsubscribe link of a re-subscribe mail uses `HMAC-SHA256("unsub|" + token, shop secret)`. The confirm page accepts a status-2 row only while the token's own time is at most 7 days old (and not more than 5 minutes in the future); its POST sets status 1, clears the token, sets `date_confirmed` and the derived unsubscribe hash (`resubscribe()`), sets the customer newsletter flag and counts the sign-up. As a second line of defence `saveSubscriber()` can no longer change a status-2 row at all (`IF(status = 2, …)` in the update list) and `confirmSubscriber()` only confirms status-0 rows; the admin can only export or erase sign-ups.
- **Storefront script (shared with the WordPress edition):** a cart change that happened while a cart refresh was still running was lost — it is now refreshed again afterwards (`cartAgain`). `announcement_bar_pro.js`, `announcement_bar_pro_pre.js` and `announcement_bar_pro.css` are byte-identical in OpenCart 3, OpenCart 4 and WordPress; `build.sh` also compares them with `../announcement-bar-pro-wordpress/announcement-bar-pro/assets/` when that folder exists, and both kits' `.gitattributes` keep the two JS files on LF.
- Schema stays 8: the Turnstile keys are ordinary settings (no migration); upgrading 2.4.0 → 2.4.1 replaces files only.
- **Compatibility pass (2026-11-08, OpenCart 4 package only; see `COMPATIBILITY.md`):** OpenCart 4.0.0.x–4.0.1.x: the double opt-in e-mail was not sent through the shop's SMTP settings — their `Mail` class takes the engine only and reads the options from public properties, so the options are now also set as properties there (`version_compare(VERSION, '4.0.2.0', '<')`); 4.0.2.0+ unchanged. OpenCart 4.1.0.0: its `catalog/category.autocomplete` matches whole names only, so the category picker (message form) now uses the module's own search (`…announcement_bar_pro.categories` / `|categories`: names containing the text, shown with their path, 10 at most, same answer format).

## 2.4.0 — 2026-11-07
- **Several bars at once + priority:** every message has a place — the module's bar position (default, unchanged for existing messages), top bar, bottom bar, or an inline box on the **cart page** (under the heading / above the cart list), **under the product price** and in the **mini-cart** drop-down (an `<li>`, so OpenCart 3's `ul li` AJAX reload keeps it). Inline boxes come from new OpenCart events (`checkout/cart`, `product/product`, `common/cart` views) and fail silently when the theme has no such spot. Priority 0–100 orders messages in every bar / box; **Messages per bar** (0 = all) shows only the highest ones. Styles and scripts are printed once per page; with one bar its id stays `abp-bar` (the second is `abp-bar-bottom`).
- Fixed: the privacy-policy link in the e-mail sign-up form was HTML-escaped twice (`&amp;amp;`), so it could open the wrong page.
- **Country targeting** (only in / everywhere except): the visitor's country comes from the shipping / payment address chosen in this visit, else the logged-in customer's address, else CloudFlare's `CF-IPCountry` header (only when switched on in Settings, which also uses `CF-Connecting-IP` for the rate limit — and only on requests that come from CloudFlare's published IP ranges), else the store country — or "unknown" (configurable). No external services.
- **Free shipping:** per-country / per-region amounts (default currency; a region row wins over a country row), fixed amounts per currency (compared with the subtotal converted to that currency — no rounding surprises), or the amount of OpenCart's own **Free Shipping** method (the message hides while that method is off).
- **OpenCart coupon:** pick a coupon from Marketing → Coupons (autocomplete); its code is shown with Copy and the message hides itself while the coupon is disabled, not started, expired, used up (total or per customer) or needs a login the visitor does not have — OpenCart's own rules.
- **Tiered goals** (new message type): 2–5 rising amounts with a reward name per language (`{goal}`), optional own text per tier, `{remaining}` to the next tier, success text when all are reached, and a multi-step progress bar with markers and reward names (names hidden on phones). Updated after AJAX cart changes like free shipping.
- **Cart conditions:** subtotal from / to, number of items from / to, cart contains one of the products / a product of one of the categories. Messages are rendered hidden when the conditions do not hold and appear / disappear after AJAX cart changes (same read-only endpoint as free shipping).
- **Campaign / referrer / new or returning visitor:** `utm_source`, `utm_medium`, `utm_campaign` (comma lists, case-insensitive) and referring domains (sub-domains included), remembered for the visit in `sessionStorage`; new vs returning from one first-party `localStorage` value ("new" for 30 minutes). With Do Not Track / Global Privacy Control / `window.abpConsent = false` nothing is stored or read: the URL campaign still counts on that page, the visitor is neither new nor returning. Decided before the first paint (no flash).
- **Triggers:** after N seconds, after scrolling N %, on exit intent (mouse leaves through the top edge; computers only). Once fired, the message shows at once on the next pages of the visit (`sessionStorage`). The bar slides in (no animation with reduced motion).
- **Recurring countdown:** `{countdown}` to a daily cut-off (with days to skip) or a weekly cut-off, in store time, without an end date; when the time is up the timer starts for the next cut-off instead of hiding the message.
- **E-mail sign-up:** optional form in a message (field, button, unticked consent box with a link to a chosen information page, per-language texts with defaults). Double opt-in (default on) through the shop's own mail settings: the e-mail link opens a page with a confirm button (mail scanners confirm nothing), then customer accounts with that address get OpenCart's newsletter flag and guests stay in the module's list. Unsubscribe link in every confirmation e-mail. Endpoint: POST only, same-origin only, session-bound HMAC form token (no session write), honeypot, rate limit 10 per visitor and 200 per shop per hour, never reveals whether an address exists. Admin: counts, CSV export (formula-safe) and erasure of an address (POST, *modify*). Statistics: confirmed sign-ups only (counter), never addresses. Not shown in marquee mode.
- **Look:** background image from the image manager with an adjustable colour overlay; system font stacks only (module setting + per message; nothing is downloaded); custom CSS in Settings, filtered on save and on output (no `<`, CSS escapes, `@import`, `javascript:`, `expression()`, `behavior`, `-moz-binding`, non-image `url()`).
- **Auto-hide:** after N seconds (not while hovered / focused) the bar folds into a small labelled tab (`aria-expanded`, `aria-controls`) that opens it again; stays folded for the rest of the visit.
- **13 templates** (EN / LV / RU, others get English): free shipping, reward tiers, flash sale, same-day cut-off, welcome coupon, newsletter, new arrivals, back in stock, holiday, weekend offer, exit-intent offer, B2B, privacy-friendly shop. One click fills a new message; nothing is saved until you save.
- **GA4:** `abp_view`, `abp_click`, `abp_copy`, `abp_subscribe` through `gtag` (or a GTM `dataLayer`) when the shop already loads it — message number, A/B version and place only, once per session; off with DNT / GPC / `abpConsent = false` or in Settings.
- **Accessibility:** pause / play button for rotating and scrolling messages (WCAG 2.2.2), labelled form controls with `aria-invalid` and a live status, visible focus on every new control, 24 × 24 px minimum targets, reduced motion respected. Statistics now also respect `window.abpConsent = false`.
- **Admin:** new cards (Templates, Free shipping & goals, E-mail sign-up, Placement & behaviour, Audience, Cart conditions) in the 2.3.0 card design; the live preview shows tiers, the e-mail form, background image, fonts, recurring countdowns, bottom bars and inline boxes. Every badge in the message list has a visible label (2.3.0 review: the targeting badge showed an icon only). Settings: messages per bar, auto-hide, pause button, font, custom CSS, visitor country (CloudFlare, fallback), e-mail sign-ups (privacy page, double opt-in, counts, export, erase), GA4. All new strings in English, Latvian and Russian; storefront texts too.
- **DB schema 8:** `abp_message.placement`, `priority`, `options` (JSON, validated on save and again on read), `subscribes`; `abp_message_description.extra` (JSON, ASCII only so OpenCart 3's 3-byte utf8 link keeps every character); new tables `abp_subscriber` (token hashes only) and `abp_rate` (keyed hashes, expire). Same idempotent migration as before (`SHOW COLUMNS` before every `ADD COLUMN`), upgrades from schema 6 and 7, the `_schema` value written last; until then the storefront runs exactly as 2.3.0. A per-shop secret for the form tokens is created once. Messages that use none of the 2.4.0 features keep their dismiss keys (closed stays closed).
- Export / import carry placement, priority, options and the extra texts.
- **Fixes from the pre-release review:**
  - *E-mail header injection (high):* `FILTER_VALIDATE_EMAIL` accepts quoted local parts such as `"a\<LF>X-Injected:1"@a.co`, which reached the mail's To header / SMTP `RCPT`. Addresses with any control character, quote or backslash are now refused, and every value that goes into a mail header (address, sender name, subject) is stripped of CR / LF.
  - *CloudFlare headers:* `CF-Connecting-IP` and `CF-IPCountry` are trusted only when `REMOTE_ADDR` is inside CloudFlare's published IPv4 / IPv6 ranges (built into `features.php`, dated; CIDR match for both families); otherwise `REMOTE_ADDR` and no header country. Before, anyone could fake both while the setting was on.
  - *Sign-up without double opt-in:* customer accounts' newsletter flags are no longer changed and unsubscribed addresses are no longer subscribed again (same answer as for a new address, nothing changes). At most 3 confirmation e-mails per address in 24 hours (keyed hash of the address in `abp_rate`). The per-visitor and per-shop hourly limits are settings (defaults 10 / 200). Cloudflare Turnstile was left out: it needs a third-party script, keys and a server-side call per sign-up.
  - *Coupon dates:* the code is shown only while OpenCart itself accepts the coupon — `date_start < NOW()` and `date_end > NOW()` in SQL, as OpenCart 3 does (4.1 compares the same values in PHP; both use the same clock) — so it is hidden on its end date, not a day later.
  - *Wait for cookie consent* (new setting, off by default): A/B, the new-visitor memory, campaign memory, statistics and GA4 start only when `window.abpConsent === true`; a later consent is picked up through the `abp:consent` event (README).
  - *Cart endpoint:* the ids are validated first and a request without valid ids returns at once without a rate-limit write; the limit is 1200 requests per 10 minutes per visitor (was 300), which normal shopping never reaches but still stops scripted floods.
  - *Build:* `build.sh` now checks that `features.php` is byte-identical below the shared-body marker in both kits (sed + cmp) and has LF line endings; the OpenCart 3 copy was converted to LF and both kits got a `.gitattributes` (`*.php`, `*.twig`, `*.css`, `*.json`, `*.xml` → LF).
- Shared code: the new `features.php` library (options, targeting, goals, cut-off times, CSS filter, tokens, templates) has a byte-identical class body in both kits; `build.sh` checks it like the shared JS / CSS.
- Tested on real OpenCart (MariaDB 11.4, Chromium, local SMTP sink): 3.0.5.1 upgrade 2.3.0 → 2.4.0 with 3 messages + every feature through the admin UI and storefront (1366 / 390 px, contrast, no horizontal scroll from the module, no JS errors, no PHP log entries) 133/133; 4.1.0.4 fresh install 123/123; schema + feature-library + controller unit test 191/191; demo test 64/64 (after the review fixes).

## 2.3.0 "Pro Max" — 2026-11-07
- Review hardening: the free-shipping endpoint answers only for messages of the visitor's store and customer group (same rules as the bar); it also accepts read-only requests without origin headers (older Safari with a no-referrer policy), statistics stay strict. The A/B variant is not stored (everyone sees A) with Do Not Track / Global Privacy Control, or when the shop's consent tool sets `window.abpConsent = false`. The threshold help says it is the same rule as OpenCart's Free Shipping method.
- Admin live preview shows the store's icons: the icon font is embedded into the sandboxed preview (the browser blocks fonts there without a CORS header). Icon-only badges in the message list have screen-reader text.
- Author is now **3DP SIA**; the extension link opens the support e-mail extension@3dp.lv (`install.xml`, `install.json`).
- **Free-shipping progress** (new message type): amount in the store's default currency, a per-language text with `{remaining}` and a per-language text for when the amount is reached (required where the text is set), optional thin progress bar. The remaining amount is computed on the server from the cart subtotal (without tax) and formatted in the visitor's currency. After OpenCart's own AJAX cart requests (`checkout/cart` and `common/cart` routes, OpenCart 3 and 4, via jQuery `ajaxComplete`) the bar asks a small read-only endpoint (`…/cart`, GET `ids`, same-origin only, JSON, no session changes beyond what OpenCart does on any page view, never outputs errors) and updates text and bar in place.
- **Coupon code with Copy:** optional per message (A–Z, 0–9, `-`, `_`, max. 32, stored uppercase). Dashed code chip + Copy button (Clipboard API with `execCommand` fallback), visible "Copied!" feedback announced through `aria-live`, new **copies** counter.
- **A/B test:** optional variant B per message (text, phone text, button text) behind a checkbox. Every browser gets a stable random variant (`localStorage` `abp_ab`, without storage: A). Views, clicks and copies are counted per variant; the admin list shows both CTRs and stars the better one once each variant has at least 100 views. **Use B as the main text** (POST, *modify*, `user_token`, double-click safe) copies B into A in every language that has a B text, switches the test off and keeps B's counters as the main counters.
- **Weekly schedule:** weekdays (any subset) and an optional daily window HH:MM–HH:MM that may cross midnight (it belongs to the day it starts on), in the store's time zone, together with the start / end dates. Checked on the server at render; messages outside their window are rendered hidden and the script switches them on and off while the page stays open (server clock + store time-zone offset, so a wrong visitor clock does not matter). Server and script share the same rules (unit-tested in PHP).
- **Category / product targeting:** optional lists (max. 200 each) chosen with autocomplete chips that use each OpenCart version's own catalog autocomplete route (`catalog/category/autocomplete` / `catalog/category.autocomplete`, `|` before 4.0.2.0). With lists set, a message shows only on those category pages, on product pages of those products and on product pages of products in a chosen category; works together with pages, stores, customer groups and devices. Unknown IDs are rejected.
- **Export / import (JSON):** Export downloads every message (texts keyed by language code, statistics left out). Import accepts our export format up to 1 MB, maps language codes to this shop's languages (unknown ones are skipped and listed), runs every message through the same normalisation, validation and sanitizing as the form and creates it switched off; the result reports created / skipped. *modify* + `user_token`; the file content is never trusted.
- **Design — storefront:** module-wide **Style** setting with a per-message override: Solid, Gradient (derived from the bar colour), Soft (light tint, dark text), Minimal (near-white with a thin top accent line) and Glass (translucent with backdrop blur, solid where the browser cannot blur). Every style keeps the automatic-colour logic and a contrast of at least 4.5:1 (Glass is checked against both a white and a black page behind it; custom colours below 4.5:1 are corrected in the derived styles, Solid custom colours are still not changed). Pill buttons (filled / outline / link per message), SVG close icon, refined typography (font inherited from the theme), smooth progress bar, rotation effect **fade | slide**, optional **prev / next arrows** (buttons with labels, keyboard accessible), `prefers-reduced-motion` respected, no horizontal scroll from 320 to 1920 px. The phone / desktop rules of 2.2.0 are unchanged.
- **Design — admin:** each version's own Bootstrap (3 / 5). The message form is grouped into cards (Content, Button & coupon, Free shipping, A/B test, Schedule, Targeting, Appearance) with one language switcher for all per-language fields and a sticky **live preview** that loads the shop's real storefront CSS / JS from the catalog URL into a sandboxed frame (computer / phone width, version A / B, cart below / above the amount) and updates while typing. The list has a colour swatch, status badges, badges for free shipping, coupon, A/B, schedule, targeting, device and missing languages, views / clicks / copies and CTR (per variant for A/B). Settings are grouped with help texts and a visual style picker. The admin script and styles are shared byte-identical by both kits (`build.sh` checks them too).
- **DB schema 7:** `abp_message` gets `type`, `threshold`, `progress_bar`, `coupon`, `copies`, `ab_test`, `views_b`, `clicks_b`, `copies_b`, `weekdays`, `time_start`, `time_end`, `categories`, `products`, `style`, `button_style`; `abp_message_description` gets `success_text`, `text_b`, `mobile_text_b`, `link_text_b`. Same idempotent migration as 2.2.0 (`SHOW COLUMNS` before each `ALTER TABLE … ADD COLUMN`), only for users with *modify* permission; upgrades from 2.1.x get the 2.2.0 columns in the same run. TEXT columns have no `DEFAULT` (MySQL refuses it). Existing messages keep the 2.2.0 outline button (`button_style` default `outline`; new messages start with `filled`). Until the admin page is opened the storefront keeps working on the old schema (neutral values for the new columns, no cart endpoint).
- **Upgrade safety:** messages, settings and the per-message dismiss keys are kept — a message that uses none of the 2.3.0 features has exactly the same key as in 2.1.x / 2.2.0, so closed messages stay closed.
- New strings in English, Latvian and Russian (admin), Copy / Copied / previous / next in the storefront.
- Fix found by the real-shop test: admin links printed with `|e` were escaped twice (`&amp;amp;`), which lost `user_token`; links already HTML-encoded by OpenCart are printed as they are. Fix: the admin stylesheet link must not sit between `column_left` and `#content` (OpenCart 3 positions `#content` with a sibling selector). OpenCart 4 admin model: no notice when a message without `device` is saved.
- Tested on real OpenCart (MariaDB 11.4, Chromium): 3.0.5.1 upgrade 2.2.0 → 2.3.0 with 2 messages + every feature through the admin UI and storefront (1366 / 390 px) 72/72; 4.1.0.4 fresh install 63/63; schema unit test 95/95; demo test 50/50.

## 2.2.0 — 2026-11-07
- **Phone text (optional, per language):** a short text that replaces the normal text on screens narrower than 768 px. Both texts are rendered and a CSS media query switches them. Same sanitizing and HTML-mode rules as the text, `{countdown}` works in it, and it is part of the per-message dismiss key (messages without a phone text keep their 2.1.x key, so closed messages stay closed after the upgrade).
- **Device targeting per message:** all devices / computers only (768 px and wider) / phones only. Messages for the other screen size are hidden by CSS and left out of rotation, marquee and stack; the script rebuilds the bar when the viewport crosses 768 px (rotation, resize). With nothing left, the bar hides and header offsets are restored exactly as when it is closed.
- **Statistics (counters only):** views and clicks per message, CTR in the admin list, "Reset statistics" per message. The storefront sends one view per message per browser session when the message is really shown, and one click when its button or a link in it is used (`navigator.sendBeacon`, fallback `fetch` keepalive). Nothing is sent when the visitor has Do Not Track or Global Privacy Control on. The endpoint (`…/track`) accepts only POST `id` + `type` (view/click), counts only enabled messages, at most one view and one click per message and 100 events per OpenCart session, always answers with an empty 204 and never outputs errors. No personal data is stored and the module sets no cookies of its own.
- **Duplicate** a message from the list: all languages and settings are copied, the copy is switched off and starts with zero statistics.
- DB schema 6: new columns `abp_message.device`, `views`, `clicks` and `abp_message_description.mobile_text`. Upgraded shops get them through an idempotent migration (`SHOW COLUMNS` check before each `ALTER TABLE … ADD COLUMN`), run when a user with *modify* permission opens the module page. Until then the storefront keeps working with the 2.1 columns.
- `mobile_text` is `TEXT NOT NULL` without a `DEFAULT`: MySQL refuses a literal default on `TEXT` columns. Existing rows get `''` when the column is added and every insert sets the value.
- New admin strings in English, Latvian and Russian.
- Hardening after review and real-shop tests: the statistics endpoint never touches the visitor's session (no race with cart or login), counts only same-origin requests and messages inside their date window; older browsers' Do-Not-Track values are honoured; no width gap between the phone and computer rules; a double click on Duplicate creates one copy (both versions). OpenCart 3: Duplicate and Reset are plain buttons that post their own form (the admin's "submit every form" helper for IE submitted the settings form instead).
- Tested on real OpenCart: 3.0.5.1 upgrade 2.1.2 → 2.2.0 with 2 existing messages (migration, idempotency, phone text, device, statistics, duplicate, reset, error log) 22/22; 4.1.0.4 fresh install 15/15.

## 2.1.0 — 2026-11-06
